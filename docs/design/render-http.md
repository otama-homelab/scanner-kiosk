# Render admission HTTP

`POST /api/documents/{document_id}/render` now connects the authenticated HTTP boundary to the existing durable render admission and worker pipeline. It requires Origin, Idempotency-Key, quoted positive If-Match and JSON. It returns 202 with the owned job projection and same-origin Location. Browser review offers Create PDF (documents) or the current JPEG image export action (photos), then navigates to the real job screen. Once a current output exists, Download is shown instead of an unnecessary recreate action.

The request accepts PDF/JPEG/PNG, PDF jpeg/lossless encoding and the OCR selection schema. The decoder rejects unknown fields, nested duplicate keys, nulls, invalid UTF-8, trailing JSON, missing required values and server-only model version/reservation parameters. Body size is capped at 64 KiB. The store validates purpose, page set, enabled principal, revision, state, resource limits and TTL in its existing transaction. Stale revision returns 412; active-state/idempotency conflicts 409; quota failures 429. The endpoint does not launch processing inside an HTTP transaction.

`renderadmission.Service` is an HTTP-neutral port over the document store plus an OCR resolver interface. It reconciles an existing receipt before looking up current OCR capabilities or reserving space. The shared v1 digest/receipt reader is also used by direct store admission; a fixed historical digest regression test proves old receipts remain readable. Client model-version, resolved-preset and quota fields are never trusted. New work conservatively reserves the configured whole-job byte ceiling. This may admit fewer small concurrent jobs than a future measured estimator, but cannot silently bypass the worker's existing budget. The actual transaction observes per-user/global reservations and pinned-filesystem headroom.

For OCR, the service can pin a resolved model version and default quality preset through a trusted capability resolver without importing provider factories or credentials into the API. The [catalog resolver](ocr-catalog.md) consumes a read-only worker publication source in API composition. Active validated metadata pins model version/default preset; unsupported selections return 422, missing/stale publication returns 503. There is no fallback to plain PDF or invalidation of an existing output on rejection. Existing receipts replay even after catalog withdrawal. A real HTTP test verifies this boundary with fixture metadata, independently of provider execution. The [public capability projection](capability-http.md) is connected. Admission checks trusted model page/pixel bounds against captured source dimensions before creating work; incompatible or unknown dimensions return 422 without changing existing state. Browser OCR selection is connected through the public capability projection. The review output dialog now selects JPEG/lossless PDF encoding or JPEG/PNG photo output. The dialog also selects OCR model, languages and quality without enabling OCR by default. The fast photo action defaults to JPEG; the dialog starts from the existing output format when known. PDF encoding defaults to JPEG for a new command because the current public output projection does not expose its prior encoding.

Tests cover strict commands, duplicate fields, rejected server parameters, unavailable OCR without fallback, single admission/reservation under replay, changed intent, policy-owned reservation, model pinning and provider-independent replay. Browser verification submits a real render command for a synthetic captured PNG, invokes the actual compiled worker with `--once`, follows the durable job to succeeded, opens the document and saves scan.pdf through Chromium's download mechanism. The proxy's worker-launch endpoint is a test fixture only; the product uses its separate worker process. Cancellation terminal-state injection is still explicitly a fixture and does not prove scanner/process stop. Browser OCR admission has fixture coverage and an optional real Tesseract daemon scenario through native browser download with independent per-page text/pixel checks. Real acquisition, live LLM OCR, production scan dispatch/recovery, actual mobile downloads and deployment remain pending.
