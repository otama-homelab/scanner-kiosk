# Render cancellation and heartbeat monitor

`documents.PulseRender` renews heartbeat only for the enabled owner's claimed running render with exact runner, current document revision, processing state, unexpired deadline/retention and outstanding reservation. Missing/foreign/stale/cancelling work is rejected. The immutable start timestamp is untouched. A pulse never transitions a job to a terminal state or releases files, reservations or device leases.

`workwatch.Run` checks the pulse before invoking work, then pulses periodically using the processing context. The interval is bounded to one millisecond through one minute; the executable worker must choose its actual operational policy. Pulse failure cancels the context with the original error, including storage/uncertain-commit errors. Parent cancellation also propagates. On normal completion it cancels an in-flight monitor request and joins the monitor before returning, without turning completion-driven monitor cancellation into a processing error. Work must cooperate with context cancellation: this helper cannot kill a native child or certify process exit.

`renderjob.PrepareWatched` connects this monitor to ordinary PDF preparation. PDF input access, generation and the job-deadline context receive cancellation. If preparation finishes just as monitoring rejects the job, the completed unpublished result goes through `Prepared.Finish` with bounded independent cleanup context. Publication continues to recheck DB state even after monitored preparation succeeds. An initial rejection does not create a workspace. `ExecuteClaimed` now connects failure before a normal Prepared object to confirmed cleanup reporting and terminalization; unknown cleanup remains held for reconciliation.

Race-enabled tests cover heartbeat/start separation, lost owner/runner/revision, cancellation/expiry/deletion, pulse errors, parent cancellation and joining a blocked monitor. A real SQLite test persists cancellation during watched work and observes context cancellation while reservation remains held. PDF component tests cover actual watched generation and rejection before generation. These tests do not prove native process interruption, a production polling latency, executable scheduling, restart recovery or real-device behavior.
