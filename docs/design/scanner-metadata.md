# Verified scanner settings

The enabled worker now publishes read-only scanner metadata to the capability API. This stage does not initialize idle leases or mark scanners ready. Readiness-gated scan HTTP admission is connected; production handoff/readiness, capture settings/selection UI and physical-writer acceptance remain pending.

`scannerdriver.InspectCapture` inspects one complete size/color/DPI combination on a registered device. It shares the same selection read-back, native parameter validation, local process-stop and owned inspection cleanup path as the claimed-job resolver. Metadata inspection does not consume the job's one-use resolver entry, allocate a capture attempt, call acquisition, observe physical idle or change durable work. Job resolution still repeats the native inspection rather than trusting cached geometry. Dimensions before acquisition remain best-effort and actual captured images are validated again.

`scannermetadata` defines the backend-neutral Inspector/Source ports and bounded snapshot model. The current domain is flatbed, five paper sizes, color/gray and 75/100/150/200/300/600 dpi, with at most 32 devices and 60 tuples per device. Snapshots reject duplicate devices/tuples, unsupported enums, invalid dimensions, future observations and observations beyond a five-minute bound. A successful tuple does not imply support for any other combination.

## Worker and authority

Only SCANNER_ACQUISITION_ENABLED=true constructs the native Session and starts the metadata publisher. It remains false by default. Configure itself still performs no native/status IO; enabled runtime inspection is an explicit additional lifecycle step. Inspection runs separately from coordinator heartbeat, OCR publication and plain rendering, with each device's driver gate serializing it against that device's capture. Each device batch has a 30-second context budget. A fixed pool runs at most four device inspections concurrently; configured devices are queued without duplicating an outstanding task. The default A4/color/300 tuple is queried first, then the remaining bounded candidates. Known rejected tuples are omitted; unresolved stop/input/cleanup state stops the worker and retains resources rather than publishing a partial result.

Completed profile sets are cached per device for one minute to avoid reopening every backend for each heartbeat. A single publisher merges completed device results immediately without waiting for other batches, and republishes at one third of the coordinator lifetime. Pending or failed batches never replace another device's verified set. Timed-out batches discard that device's unfinished set and become eligible to retry after a publication interval. A complete empty set retries after the usual minute. The bounded queue still means a device can wait for an inspection slot when all four are busy; no unbounded native fan-out is introduced. Each native observation retains its original check time; a fresh heartbeat/publication cannot extend it past five minutes. The historical SCANNER_OCR_CATALOG_LEASE_SECONDS setting currently supplies the shared processing-metadata authority lifetime as well. No physical-idle or exclusive-writer assertion is derived from it.

Document migration 0007 adds one scanner_metadata_snapshot row under the current processing coordinator boot/generation. Publication uses the live document-root guard and checks authority in the same short transaction. Native processes/network requests do not run inside this transaction. Check times must be at or after the coordinator's creation time, so a new boot cannot reuse an earlier worker's cached observation. Snapshot expiry is bounded by both authority and observation age. Before publication, a device whose oldest observation cannot outlive the next publication interval plus two seconds is removed as a whole. Its original check time is never refreshed, and removing it does not remove healthy devices. This conservative margin prevents an old device from expiring the shared snapshot before the next scheduled publication. Begin/Stop clear scanner metadata alongside OCR metadata; readers reject stale, stopped, replaced or malformed authority/payloads.

Shutdown cancels and joins the publisher and every inspection worker before metadata withdrawal and Session/config cleanup. A failure discovered while joining is returned, including when shutdown began with cancellation. An input change may be detected by the metadata goroutine before the explicit cancellation reaches it. Such a run retains the owned tree with ErrReconciliation; it must not force an unresolved inspection into the ordinary config-cleanup path. Clean cancellation still drains normally. Repeated copies of the same authority failure preserve the original error identity.

## Public projection

`GET /api/capabilities` now reads scanner metadata through a separate Source port. It returns capture_options as complete verified size/color/DPI tuples filtered by the API's deployment pixel limit. Existing sizes/colors/dpi_options are only facets; clients must not construct a Cartesian product from them. Native width/height, check times, boot/generation, tool paths and endpoints are not projected.

A scanner's default_capture is A4/color/300 only when that exact tuple is verified within the deployment limit; otherwise it is null. The top-level capture default remains the standard preference, not a device support assertion. Sources become flatbed when a verified tuple is available. Missing/expired scanner metadata leaves empty choices without making valid OCR metadata unavailable. Configured labels/IDs still bound which devices may appear. Native refresh times do not change the public content revision if selectable content is unchanged.

Native tuples alone still yield unknown state. A separate transactional readiness
Source now projects advisory idle/busy/unavailable when current trusted records
permit it; production still has no readiness evidence producer. A read-only capability observation, coordinator flock or Idle response cannot fence scanservjs or initialize device leases. The next stage must establish exclusive writer/recovery conditions and fresh idle evidence, then bind scan admission to the live coordinator/device lease inside its transaction.

## Evidence

Driver tests verify exact metadata without Capture/idle/claim state, invalid and over-budget settings, missing stop/cleanup retention and subsequent job resolution. The tagged official SANE test/helper integration inspects metadata before the real monitored virtual acquisition and publication; the fixture's native A4 result is 2480 by 3507, not a hard-coded production estimate.

Runtime integration runs the actual Session with fake native executables and local eSCL status, admits a scan through the current worker boot, and verifies both captured output and publication of only the one tuple the fake backend really accepts. Builder tests verify all 60 bounded candidates and cache reuse/refresh. Publisher tests hold one device blocked while the healthy device is published and retained without re-probing, verify the four-operation ceiling, reject new queued inspections during shutdown, preserve errors discovered while joining all workers, prune old device data independently and create no readiness lease. An unresolved native operation still stops the whole worker, never yielding new partial data after that failure is known. Store tests cover boot/generation replacement, observed-before-boot/future/duplicate/unsupported/dimension failures, stale observations despite a renewed heartbeat, expiry and withdrawal, with no ready lease created.

API tests verify coupled tuples, deployment-cap filtering, nullable defaults, private-field exclusion, stable revisions, expiry and unknown readiness. Cancellation/input-change and authority-loss tests were repeated ten times while requiring retained foreign content, reconciliation and metadata withdrawal. These are local/virtual tests; previous Canon read-only receipts remain historical evidence and do not establish real acquisition, physical exclusivity, complete restart recovery or deployment acceptance.

The repository now has a separate trusted readiness/admission boundary; see
[scanner readiness](scanner-readiness.md). Native metadata does not publish that
evidence, and the runtime still has no production handoff/readiness producer.

See [scanner status](scanner-status.md) for the OCR-independent GET /api/scanners
route, shared status projection, expiry handling and query-count evidence.
